# mindmeld update

`init` is the ritual for a machine that has nothing yet; `update` is how an existing
instance stays current, and the repair `doctor` names for nearly everything it finds
there. It converges: whatever `init` would have put down and the instance is missing —
scaffold files a release added, the hot cache, a qmd collection, a re-pointed skill
link — comes back, and everything `init` asks a human about is left to `init`. It owns
exactly what mindmeld owns — the checkout and the organs it installs — and says so
explicitly rather than pretending to be a general-purpose updater.

## Usage

```bash
mindmeld update [--dry-run] [--copy] [--config]
```

- `--dry-run` — preview the pull and reinstall without writing
- `--copy` — copy instead of symlink — pass this if the checkout was originally
  installed with `init --copy`, or `update` will re-link a copy install into a symlink
  one, which isn't drift, it's a different posture than the one you chose
- `--config` — also rewrite the `mindmeld.toml` keys a release has moved or removed, behind
  a backup. Without it `update` only reports them. See [Config drift](#config-drift)

## What it does

Ten steps, in order:

1. **Pull.** For a managed (Homebrew) install — the common case — there's no checkout
   to pull, so this step reports `managed install — run 'brew upgrade mindmeld' to
   update the engine` and stops there: brew owns the version bump, `update` owns
   everything after it. For a source checkout, this step runs `git pull --ff-only`
   instead — no upstream configured, or the checkout has local changes, both degrade to
   a warn-and-skip; `update` never stashes, forces, or rebases over a stranded edit.
2. **Converge the KB scaffold.** Runs `init`'s copy-if-absent pass over the existing KB,
   so a file a release added reaches an instance initialized before it: policy files,
   the instruction pair, `.gitignore`, and the rest of the layout under
   [The KB instance](../config.md#the-kb-instance). It never prompts — the owner comes
   from `mindmeld.toml`, and a fresh `OWNER.md` carries the same placeholder `init
   --defaults` writes — and it never rewrites a file that exists. A pre-split KB (a
   hand-authored `CLAUDE.md`, no `AGENTS.md`) is left as it is, exactly as `init` leaves
   it. With no `[kb].root` configured this step warns and points at `mindmeld init`.
   It runs ahead of the adapter install for the same reason it does in `init`: the
   `CLAUDE.md` shim is only written when `AGENTS.md` exists, so one update leaves both.
   Under `--dry-run` the shim preview follows the same ordering, so a dry run on an empty
   KB says `would write <kb>/CLAUDE.md (@AGENTS.md shim)`, as the real run then does.
3. **Reinstall the adapter.** The exact step `init` runs — same link/copy/backup
   semantics, byte-identical report lines — so any skill or hook that drifted back to a
   real path or a foreign symlink gets repaired. This is also what re-materializes the
   `CLAUDE.md` shim if it's missing: the shim is generated by the adapter, not by
   `kb-scaffold`, so `update` gets it for free rather than needing its own step. See
   [Adapters](../adapters.md). It's also the repair for a moved checkout: the registered
   `mcp` command is derived from the checkout root every time, never remembered, so a
   checkout that's moved since the last `init` re-points at its new location the next
   time `update` runs — the same reason a stale skill symlink gets repaired here rather
   than needing its own verb. `update` gains a prompter for this one question only when
   it's running on a TTY; a non-interactive run (CI, `cron`, the install sim) keeps
   writing unattended so "update re-registers" stays true off a terminal too.
4. **Refresh the guide.** Restamps `{kb.root}/docs/mindmeld/` the same way
   `mindmeld docs install` does: new pages get stamped, changed ones refreshed, and a
   page you've edited out of the marker is left alone. See [mindmeld docs](docs.md).
5. **Refresh the adapter notes and manifest.** The same marker-guarded restamp, for the
   active adapter's `notes.md` and `manifest.json` under `{kb.root}/adapters/`.
6. **Seed the hot cache.** `wiki/_hot.md`, the session-start pulse cache, regenerated the
   way `init` does it — without the consent prompt, since you answered that once at setup.
7. **Register the qmd collections.** The KB-root collection, plus the `candidates` and
   `patterns` scoped pair excluded from default queries. Each is checked against what
   qmd already lists first, so a collection that's present (and, for the pair, already
   excluded) is silent. A missing `qmd`, an unresolvable lock identity (reported once, here, with
   its real cause: `qmd lock identity could not be resolved (<cause>) — collection
   registration skipped`), or a failed listing is a warn and the run continues: the
   collections are a repair target here, not a precondition. A new registration is reported with what fills it:

   ```text
   − [update] qmd collection <name> registered — run 'mindmeld reindex' to embed it
   ```

   `update` **never embeds**. Registering is cheap; the embedding pass is `mindmeld
   reindex`'s, and an update that ran it would contend with the reindex a hook or a
   mining run already holds the index lock for.
8. **Sync bases.** Brings every shipped `.base` board current against your KB via the
   same seed-tracked three-way merge `init` runs on a fresh KB — an edited board is
   never destroyed, only replaced or merged when the seed proves your copy hasn't
   diverged from what was last stamped.
9. **Sync templates.** The identical seed-tracked three-way merge, applied to
   `templates/`: a shipped template is no longer copy-if-absent, so a correction to one
   (a schema fix, not just prose) now reaches an existing KB the same way a board's
   does. A template installed before this mechanism existed and never edited since is
   recognized once against a small, closed registry of historical shipped content and
   folded into the ordinary sync in the same run — see
   [Your KB, directory by directory](../kb-layout.md#the-seed-how-ownership-is-tracked-and-handed-off)
   for the seed's own ownership-handoff rule, which applies to templates exactly as it
   does to boards.
10. **Check the config for drift.** Reads `mindmeld.toml` for keys a release has moved or
    removed, and with `--config` rewrites them. See [Config drift](#config-drift).

A configured `[kb].root` that isn't a directory — a KB this machine hasn't cloned yet,
an unmounted volume, a typo — skips every KB-side step (the scaffold, the guide, the
adapter notes, the hot cache, the qmd collections, the boards and the templates) with one
warning, rather than standing up a fresh, disconnected KB there that a later `init` would
refuse to clone over:

```text
− [update] kb root <path> does not exist — skipped the KB steps; run 'mindmeld init'
```

The pull, the adapter install and the config check don't touch the KB root and still run.

What stays `init`'s alone is what needs a person at first install: the preflight offer
to brew-install missing tools, picking the KB root and owner, writing `mindmeld.toml`
itself, and cloning the KB from a remote. `update` assumes those happened.

## Config drift

A release occasionally moves a `mindmeld.toml` key to a new table, or stops reading one.
The old line then sits in your file doing nothing, which is exactly the shape of a bug
that takes an afternoon to find. `update` reads the file for these and says so, whether or
not you pass `--config`:

```text
− [update] [mining.recurrence] reindex_timeout has moved to [reindex] timeout — the value here is ignored — rerun with --config to apply
✓ [update] config: 1 newer key(s) unset, defaults in force — [reindex] timeout (10m)
```

The second line is informational: keys added in a release that your file doesn't set,
with the default in force. `update` never writes one, because writing a default would pin
today's value and quietly opt you out of the next change to it.

With `--config`, `update` rewrites the moved and removed lines:

1. It checks the rewrite before touching anything: the result must still parse, the old
   key must be gone, and a moved value must read back unchanged at its destination.
2. It copies the file to `mindmeld.toml.pre-mindmeld-<timestamp>` beside it (a numeric
   suffix on a same-second clash; the original's permissions kept).
3. It replaces the file with a temp-file-and-rename write, so an interrupted run leaves
   the old file or the new one. A symlinked config is written at its target, so a
   dotfile manager's link survives.

The rewrite is line-level: comments, ordering and every line it doesn't edit come through
byte for byte, and a moved key keeps its trailing comment. It handles one shape — a
single-line `key = value` under its own `[table]` header. Anything stranger is left alone
and reported with why:

```text
✓ [update] config: backed up <path> to <path>.pre-mindmeld-20260101-120000
✓ [update] config: moved [mining.recurrence] reindex_timeout to [reindex] timeout
− [update] <the drift sentence> — edit by hand: <reason>
```

The first two are the applied case, one line per drift after the one backup line. The
third is the refusal form. A second `--config` run finds nothing to apply and writes no
second backup. When a rewrite can't be backed up, written, or proven correct the file is
left untouched and the line is an error.

A config file its owner can't write is refused outright: `--config` is a deliberate
"don't touch" signal on a read-only file, not a permission to work around it, so every
moved or removed key reports the refusal form with the file named as the reason, and
nothing is backed up or written:

```text
− [update] <the drift sentence> — edit by hand: mindmeld.toml is read-only
```

`--dry-run --config` prints each rewrite as `would rewrite <path>: moved … to …` under the
`dry-run` tag and writes nothing, backup included. It applies the same read-only refusal,
so the preview matches what the real run would do.

## Upgrading across the journal-format change

**Required once, when upgrading from a build that predates kind-qualified run journals.**

A running ritual's journal used to be named `journal.jsonl`; it is now named for its
ritual, `spawn-session.journal.jsonl` beside `wrap-session.journal.jsonl`, so a branch
can hold one run of each kind. The new build takes a lock around claiming a journal. An
older build does not take that lock and does not know the new names, so the two cannot
coordinate — and `update` replacing the binary on disk does not replace a copy of the
engine that is **already running**.

Every open Claude Code session that has Mindmeld loaded holds its own long-lived
`mindmeld mcp` process, started when that session began. Those keep running the old
build after `update` finishes. So, after upgrading:

1. **Stop or restart every session with Mindmeld loaded** that can reach the same dossier
   root — quit and reopen the app, or restart each open session. A session opened after
   the upgrade is already on the new build.
2. **Only then start new ritual runs.** Until every old process is gone, an old and a new
   writer can each claim a journal for the same kind at the same branch, and neither
   will notice the other.

This is a stated boundary rather than an enforced one: nothing detects a live older
process or refuses on its account, so the guarantee of one active run per kind holds only
after that cutover. Journals written by the older build are read where they lie and need
no migration — the step is about processes, not files. The reasoning, and exactly what
the lock does and does not prove, is in
[the ritual internals page](../internals/ritual.md).

## Output

Step tag `update` (`dry-run` under `--dry-run`; the scaffold, hot and index steps carry
their own tags, as they do under `init`). Pull reports one of: checkout already
up to date, checkout updated to `<sha>`, no upstream configured — skipping pull, checkout
has local changes — skipping pull, or pull failed. The adapter reinstall and guide
refresh report the same lines `init` does for those steps, as do the scaffold and hot
steps. Sync bases and sync
templates report per file — stamped, updated, merged (with a conflict left for you to
resolve by hand), or silently nothing at all once a file has settled into its steady
state — never a single blanket "present" line for the whole directory. A closing line
states the ownership boundary:

```text
Updated the mind (checkout + installed organs). Machine config is managed separately —
run your dotfile manager's update for that.
```

When `--config` actually wrote a drift to `mindmeld.toml`, the boundary moves, because the
run owned the file too, and the closing line says so instead:

```text
Updated the mind (checkout + installed organs + mindmeld.toml).
```

The claim follows the write, not the flag: `--config` on a file with nothing to apply, a
refused rewrite, a read-only file, or `--dry-run` prints the first form, since
`mindmeld.toml` wasn't touched.

## Config it reads

`[kb].root` (and `[kb].owner`), as the scaffold, sync-bases, sync-templates, and
docs-refresh target — see [config.md#kb](../config.md#kb). `[install]` for the adapter
reinstall, `[mining.recurrence]` for the scoped-collection names the index step
registers — see [config.md#install](../config.md#install). `[mindmeld].checkout`, if the
content ring needs an explicit resolution — see
[config.md#mindmeld](../config.md#mindmeld).
