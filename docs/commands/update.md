# mindmeld update

`init` is the ritual for a machine that has nothing yet; `update` is the same repair,
scoped to a machine that already has everything and just needs it brought current. It
owns exactly what mindmeld owns — the checkout and the organs it installs — and says so
explicitly rather than pretending to be a general-purpose updater.

## Usage

```bash
mindmeld update [--dry-run] [--copy]
```

- `--dry-run` — preview the pull and reinstall without writing
- `--copy` — copy instead of symlink — pass this if the checkout was originally
  installed with `init --copy`, or `update` will re-link a copy install into a symlink
  one, which isn't drift, it's a different posture than the one you chose

## What it does

Five steps, in order:

1. **Pull.** For a managed (Homebrew) install — the common case — there's no checkout
   to pull, so this step reports `managed install — run 'brew upgrade mindmeld' to
   update the engine` and stops there: brew owns the version bump, `update` owns
   everything after it. For a source checkout, this step runs `git pull --ff-only`
   instead — no upstream configured, or the checkout has local changes, both degrade to
   a warn-and-skip; `update` never stashes, forces, or rebases over a stranded edit.
2. **Reinstall the adapter.** The exact step `init` runs — same link/copy/backup
   semantics, byte-identical report lines — so any skill or hook that drifted back to a
   real path or a foreign symlink gets repaired. This is also what re-materializes the
   `CLAUDE.md` shim if it's missing: the shim is generated by the adapter, not by
   `kb-scaffold`, so `update` gets it for free rather than needing its own step. See
   [Adapters](../adapters.md). It's also the repair for a moved checkout: the registered
   `mcp` command is derived from the checkout root every time, never remembered, so a
   checkout that's moved since the last `init` re-points at its new location the next
   time `update` runs — the same reason a stale skill symlink gets repaired here rather
   than needing its own verb. `update` gains a prompter for this one question only when
   it's running on a TTY; a non-interactive run (CI, `cron`, the install sim) keeps
   writing unattended so "update re-registers" stays true off a terminal too.
3. **Refresh the guide.** Restamps `{kb.root}/docs/mindmeld/` the same way
   `mindmeld docs install` does: new pages get stamped, changed ones refreshed, and a
   page you've edited out of the marker is left alone. See [mindmeld docs](docs.md).
4. **Sync bases.** Brings every shipped `.base` board current against your KB via the
   same seed-tracked three-way merge `init` runs on a fresh KB — an edited board is
   never destroyed, only replaced or merged when the seed proves your copy hasn't
   diverged from what was last stamped.
5. **Sync templates.** The identical seed-tracked three-way merge, applied to
   `templates/`: a shipped template is no longer copy-if-absent, so a correction to one
   (a schema fix, not just prose) now reaches an existing KB the same way a board's
   does. A template installed before this mechanism existed and never edited since is
   recognized once against a small, closed registry of historical shipped content and
   folded into the ordinary sync in the same run — see
   [Your KB, directory by directory](../kb-layout.md#the-seed-how-ownership-is-tracked-and-handed-off)
   for the seed's own ownership-handoff rule, which applies to templates exactly as it
   does to boards.

What it deliberately doesn't do: re-run the index step. `qmd collection add` and
`qmd embed` are `init`'s job alone — if `doctor` reports a qmd collection as missing or
unexcluded, the repair is `mindmeld init`, not `update`.

## Upgrading across the journal-format change

**Required once, when upgrading from a build that predates kind-qualified run journals.**

A running ritual's journal used to be named `journal.jsonl`; it is now named for its
ritual, `spawn-session.journal.jsonl` beside `wrap-session.journal.jsonl`, so a branch
can hold one run of each kind. The new build takes a lock around claiming a journal. An
older build does not take that lock and does not know the new names, so the two cannot
coordinate — and `update` replacing the binary on disk does not replace a copy of the
engine that is **already running**.

Every open Claude Code session that has Mindmeld loaded holds its own long-lived
`mindmeld mcp` process, started when that session began. Those keep running the old
build after `update` finishes. So, after upgrading:

1. **Stop or restart every session with Mindmeld loaded** that can reach the same dossier
   root — quit and reopen the app, or restart each open session. A session opened after
   the upgrade is already on the new build.
2. **Only then start new ritual runs.** Until every old process is gone, an old and a new
   writer can each claim a journal for the same kind at the same branch, and neither
   will notice the other.

This is a stated boundary rather than an enforced one: nothing detects a live older
process or refuses on its account, so the guarantee of one active run per kind holds only
after that cutover. Journals written by the older build are read where they lie and need
no migration — the step is about processes, not files. The reasoning, and exactly what
the lock does and does not prove, is in
[the ritual internals page](../internals/ritual.md).

## Output

Step tag `update` (`dry-run` under `--dry-run`). Pull reports one of: checkout already
up to date, checkout updated to `<sha>`, no upstream configured — skipping pull, checkout
has local changes — skipping pull, or pull failed. The adapter reinstall and guide
refresh report the same lines `init` does for those steps. Sync bases and sync
templates report per file — stamped, updated, merged (with a conflict left for you to
resolve by hand), or silently nothing at all once a file has settled into its steady
state — never a single blanket "present" line for the whole directory. A closing line,
printed unconditionally, states the ownership boundary:

```text
Updated the mind (checkout + installed organs). Machine config is managed separately —
run your dotfile manager's update for that.
```
